# Техническое задание: VPN Kill Switch для Windows

ТЗ v1.0

Windows 10 / 11

Все пользователи системы

## 1. Назначение проекта

Разработать автономное Windows-приложение, обеспечивающее защиту от утечки сетевого трафика при отсутствии VPN-туннеля.

Система должна автоматически блокировать весь сетевой доступ компьютера при потере VPN, контролировать запуск определённых приложений и запрещать снятие блокировки, пока хотя бы один запрещённый процесс работает.

Приложение должно работать независимо от пользовательской сессии, включая:

- выход пользователя из Windows;
- переключение между пользователями;
- блокировку рабочего стола;
- перезагрузку компьютера;
- закрытие Tray-интерфейса.

Основной принцип безопасности: отсутствие подтверждённой безопасности означает блокировку сети.

## 2. Функциональные требования

### 2.1. Контроль VPN

Поддержать обнаружение произвольного VPN-туннеля, без привязки к конкретному клиенту или протоколу:

- WireGuard;
- OpenVPN;
- IKEv2;
- L2TP/IPsec;
- SSTP;
- другие VPN, создающие сетевые интерфейсы Windows.

Необходимо учитывать, что наличие виртуального сетевого адаптера само по себе не доказывает работоспособность VPN.

Проверка VPN должна включать:

1. Обнаружение активных сетевых интерфейсов.
2. Определение маршрутов через VPN.
3. Проверку доступности контрольных адресов через VPN.
4. Контроль изменения маршрутов.
5. Проверку отсутствия обходного маршрута через физический интерфейс.

Для подтверждения работоспособности туннеля использовать минимум два независимых контрольных адреса, по возможности с разными сетями.

Проверка должна выполняться периодически, с возможностью немедленной реакции на системные сетевые события.

### 2.2. Сетевая блокировка

При отсутствии подтверждённого VPN:

- блокировать исходящий и входящий трафик;
- блокировать IPv4 и IPv6;
- блокировать DNS;
- блокировать UDP, TCP, ICMP и остальные IP-протоколы;
- блокировать трафик всех приложений;
- блокировать трафик всех пользователей Windows;
- исключить обход блокировки через физические адаптеры;
- не допускать утечки трафика при переключении интерфейсов.

Блокировка должна реализовываться на системном уровне, а не посредством изменения настроек отдельных приложений.

Предлагаемая технология: Windows Filtering Platform (WFP).

Дополнительные требования:

- правила блокировки должны переживать закрытие Tray;
- правила должны сохраняться после перезагрузки;
- при аварийном завершении управляющего процесса блокировка не должна сниматься;
- доступ к локальному IPC и управляющим механизмам должен оставаться защищённым.

### 2.3. Контроль процессов

Сервис должен иметь настраиваемый список запрещённых приложений.

Пример конфигурации:

```
{
  "blockedProcesses": [
    "app1.exe",
    "app2.exe",
    "app3.exe"
  ]
}
```

Правила:

- отслеживать запуск и завершение процессов;
- учитывать несколько экземпляров одного приложения;
- учитывать процессы всех пользователей;
- проверять список уже работающих процессов при старте службы;
- учитывать процессы, запущенные с повышенными привилегиями;
- при невозможности достоверно проверить процессы запрещать разблокировку.

Для надёжности использовать ETW или уведомления создания процессов через системный драйвер, а также периодическую сверку с фактическим списком процессов.

Важно: сравнивать не только имя EXE. В рабочей реализации следует поддержать проверку полного пути, а при необходимости — SHA-256 и цифровой подписи. Иначе злоумышленник или случайная программа сможет использовать другое приложение с таким же именем.

### 2.4. Условия разблокировки

Снятие блокировки разрешается только при выполнении условия:

\\[ UnlockAllowed = \neg ForbiddenProcessRunning \\]

При этом VPN может быть отключён: согласно выбранным требованиям, отсутствие запрещённых приложений является единственным условием разрешения ручной разблокировки.

Автоматическое восстановление доступа после появления VPN также должно учитывать отсутствие запрещённых процессов.

Если запрещённый процесс запущен:

- разблокировка невозможна;
- кнопка разблокировки недоступна;
- отображается причина блокировки;
- при попытке разблокировки через API операция отклоняется.

Ручной режим не должен предоставлять обход этого ограничения.

### 2.5. Windows Tray

Предусмотреть отдельный пользовательский интерфейс в системном трее.

## Состояния Tray

Зелёный — доступ разрешён

VPN подтверждён, запрещённых процессов нет

Красный — сеть заблокирована

VPN отсутствует или работает запрещённое приложение

Жёлтый — проверка / ошибка

Состояние VPN или процессов пока не подтверждено

Меню Tray:

- Текущий статус VPN.
- Состояние сетевой блокировки.
- Причина блокировки.
- Список запрещённых работающих приложений.
- Кнопка «Заблокировать сеть».
- Кнопка «Разблокировать сеть».
- Настройки.
- Журнал событий.
- Версия приложения.

Кнопка разблокировки всегда проверяет ограничения на стороне службы. Скрытие или блокировка кнопки — только интерфейсное удобство, не механизм безопасности.

### 3.1. VPN Kill Switch Service

Главный компонент системы.

Параметры:

- Тип: Windows Service.
- Уровень привилегий: LocalSystem.
- Автоматический запуск при старте Windows.
- Запуск до входа пользователя.
- Восстановление после аварийного завершения.
- Независимость от Tray.

Обязанности:

1. Инициализация WFP.
2. Восстановление сохранённого состояния блокировки.
3. Проверка запущенных процессов.
4. Запуск мониторинга VPN.
5. Принятие решения о разрешении или запрете трафика.
6. Обработка команд Tray.
7. Ведение журнала событий.

### 3.2. VPN Monitor

Рекомендуемые Windows API:

| API                       | Назначение                  |
| ------------------------- | --------------------------- |
| `GetAdaptersAddresses`    | Получение сетевых адаптеров |
| `GetIfTable2`             | Состояние интерфейсов       |
| `GetIpForwardTable2`      | Таблица маршрутов           |
| `NotifyIpInterfaceChange` | Изменения интерфейсов       |
| `NotifyRouteChange2`      | Изменения маршрутов         |
| `GetBestRoute2`           | Определение маршрута        |

Алгоритм:

1. Получить список интерфейсов.
2. Выявить вероятные VPN-интерфейсы.
3. Проверить состояние интерфейса.
4. Определить маршруты через него.
5. Проверить достижимость контрольных IP через конкретный интерфейс.
6. Убедиться, что обычный сетевой трафик не может уйти через физический адаптер в обход туннеля.
7. Передать результат Policy Engine.

Рекомендуемые параметры:

| Параметр                      | Значение           |
| ----------------------------- | ------------------ |
| Период активной проверки      | 2 секунды          |
| Таймаут одной проверки        | 1 секунда          |
| Количество неудачных проверок | 2                  |
| Время реакции на потерю VPN   | Цель — до 3 секунд |

Это стартовые значения, которые необходимо уточнить тестированием.

Важное ограничение универсальности: Windows не предоставляет одного универсального API, который надёжно определяет удалённый endpoint любого стороннего VPN-клиента. Поэтому для гарантированного предотвращения утечек потребуется механизм определения параметров туннеля и его транспортного соединения. Для разных VPN-клиентов могут потребоваться адаптеры интеграции. Нельзя считать произвольный виртуальный адаптер подтверждением безопасного туннеля.

### 3.3. Process Monitor

Для первой версии рекомендую:

- `CreateToolhelp32Snapshot` — первоначальная инвентаризация.
- `RegisterWaitForSingleObject` / отслеживание завершения процессов — контроль существующих экземпляров.
- ETW Kernel Process — события создания и завершения процессов.
- Периодическая полная сверка — например, каждые 2 секунды.

Для каждого процесса проверять:

- PID;
- имя EXE;
- полный путь;
- пользователя;
- время запуска;
- наличие запрещённого правила.

События создания процесса должны обрабатываться без задержки, а не только периодическим опросом.

При потере доступа к данным о процессах, сбое мониторинга или невозможности завершить инвентаризацию система должна считать проверку небезопасной и запрещать разблокировку.

### 3.4. Policy Engine

Единый компонент, принимающий решение о состоянии сети.

В нём должны находиться все правила, исключающие возможность противоречий между VPN Monitor, Process Monitor и Tray.

Рекомендую разделить:

- `NetworkDesiredState` — желаемое состояние сети.
- `NetworkEnforcedState` — фактически применённое состояние WFP.
- `VpnState` — состояние VPN.
- `ProcessGuardState` — наличие запрещённых процессов.

Это позволит обнаруживать ситуацию, когда программа считает сеть заблокированной, а системные правила фактически не применились.

## 4. Конечный автомат состояний

Предлагаю следующую модель:

STARTUP

Проверка конфигурации и восстановление WFP

LOCKED

Сеть заблокирована

Проверка VPN и процессов

VPN доступен, запрещённых процессов нет

UNLOCKED

Сеть разрешена

Запрещённый процесс обнаружен

LOCKED

Сеть заблокирована

Схема показывает автоматическое управление. Ручное снятие блокировки рассматривается отдельно.

Таблица принятия решений:

| VPN        | Запрещённые процессы          | Действие                    |
| ---------- | ----------------------------- | --------------------------- |
| Нет        | Нет                           | Заблокировать автоматически |
| Нет        | Есть                          | Заблокировать               |
| Да         | Нет                           | Разрешить автоматически     |
| Да         | Есть                          | Заблокировать               |
| Неизвестно | Любое                         | Заблокировать               |
| Любое      | Проверка процессов недоступна | Запретить разблокировку     |

При ручной команде «Разблокировать»:

- если запрещённых процессов нет — разрешить;
- если они есть — отказать;
- если проверка процессов невозможна — отказать.

При этом есть важное следствие выбранных требований: ручная разблокировка при отключённом VPN будет разрешена, если запрещённых процессов нет. Это не обеспечивает абсолютную защиту от утечки трафика. Автоматическое снятие блокировки, напротив, должно требовать подтверждённого VPN и отсутствия запрещённых процессов.

## 5. Реализация системной блокировки через WFP

Это наиболее критичная часть проекта.

### 5.1. Механизм фильтрации

Использовать собственный WFP Provider с отдельной Sublayer для Kill Switch.

Основные уровни фильтрации:

| WFP Layer                    | Назначение                    |
| ---------------------------- | ----------------------------- |
| `ALE_AUTH_CONNECT_V4/V6`     | Контроль исходящих соединений |
| `ALE_AUTH_RECV_ACCEPT_V4/V6` | Контроль входящих соединений  |
| `OUTBOUND_IPPACKET_V4/V6`    | Контроль исходящих IP-пакетов |
| `INBOUND_IPPACKET_V4/V6`     | Контроль входящих IP-пакетов  |

При включённой блокировке действует Default Deny.

Необходимо отдельно предусмотреть ограниченные исключения для:

- loopback;
- необходимого сетевого транспорта VPN;
- DHCP, если он нужен для получения сетевой конфигурации;
- служебных механизмов управления, не требующих внешнего сетевого доступа.

Эти исключения не должны становиться общими разрешениями для приложений.

### 5.2. Как не допустить утечки при переключении VPN

Например, компьютер подключён к WireGuard через Ethernet.

При отключении WireGuard физический интерфейс остаётся активным. Если просто удалить VPN-маршрут, Windows может направить трафик напрямую через Ethernet.

Поэтому порядок действий должен быть таким:

1. Заблокировать обычный исходящий трафик на физических интерфейсах.
2. Убедиться, что фильтры WFP применились.
3. Проверить состояние VPN.
4. При восстановлении VPN разрешить только необходимые пакеты туннеля.
5. Проверить работоспособность туннеля.
6. Проверить отсутствие запрещённых процессов.
7. Только после этого разрешить общий сетевой трафик через защищённый путь.

Нельзя сначала разрешать трафик, а потом применять правила.

### 5.3. Важное архитектурное решение: драйвер или без драйвера

Предлагаю двухэтапную реализацию.

MVP: WFP через пользовательский сервис

- Управление фильтрами через `Fwpm*` API.
- Постоянный Provider и Sublayer.
- Постоянные фильтры.
- Транзакционное изменение политики.
- Защита от снятия фильтров непривилегированными пользователями.

Production: WFP Callout Driver

Для более строгих гарантий добавить собственный драйвер:

- обработка сетевых пакетов на уровне ядра;
- централизованное применение политики;
- контроль состояния фильтрации;
- защита от обхода через нестандартные сетевые сценарии;
- более надёжное поведение при авариях пользовательского сервиса.

Драйвер потребует отдельной разработки, тестирования совместимости с Secure Boot, подписания и проверки установки на целевых версиях Windows.

Мой выбор: не начинать с драйвера, но сразу проектировать архитектуру с возможностью его добавления.

Принципиальное требование: перезапуск или падение службы не должны автоматически удалять действующие блокирующие фильтры. Для этого нельзя полагаться только на динамические WFP-фильтры, привязанные к жизненному циклу одной пользовательской WFP-сессии.

## 6. Хранение конфигурации

Рекомендую использовать:

`C:\ProgramData\VpnKillSwitch\`

Структура:

```
VpnKillSwitch/
│
├── config/
│   └── settings.json
│
├── state/
│   └── state.json
│
├── logs/
│   └── service.log
│
└── backup/
    └── settings.backup.json
```

Пример конфигурации:

```
{
  "version": 1,
  "vpn": {
    "mode": "auto",
    "healthCheckIntervalMs": 2000,
    "failureThreshold": 2,
    "healthCheckTargets": [
      "1.1.1.1",
      "9.9.9.9"
    ]
  },
  "processGuard": {
    "enabled": true,
    "rescanIntervalMs": 2000,
    "blockedProcesses": [
      {
        "name": "app1.exe",
        "path": null
      },
      {
        "name": "app2.exe",
        "path": null
      }
    ]
  },
  "network": {
    "defaultPolicy": "block",
    "ipv4": true,
    "ipv6": true,
    "allowLoopback": true
  },
  "manualUnlock": {
    "enabled": true,
    "requireNoBlockedProcesses": true
  }
}
```

Контрольные IP здесь приведены как пример: сами по себе они не подтверждают VPN. Проверки должны выполняться через нужный интерфейс и не допускать fallback через физическую сеть.

ACL для каталога должны разрешать изменение конфигурации только администраторам и SYSTEM. Пользователям предоставляется только чтение статуса и разрешённые управляющие команды.

## 7. IPC между Tray и Service

Использовать Windows Named Pipes.

Пример команд:

| Команда            | Назначение                            |
| ------------------ | ------------------------------------- |
| `GetStatus`        | Получить состояние системы            |
| `GetVpnStatus`     | Получить статус VPN                   |
| `GetProcessStatus` | Получить список запрещённых процессов |
| `LockNetwork`      | Принудительно заблокировать           |
| `UnlockNetwork`    | Запросить разблокировку               |
| `GetConfig`        | Получить конфигурацию                 |
| `UpdateConfig`     | Изменить настройки                    |

Для каждой команды Service самостоятельно проверяет полномочия пользователя и бизнес-правила.

Named Pipes должны иметь ACL, ограничивающий доступ. Запрещено доверять переданному Tray значению вроде `canUnlock=true`: решение принимает только служба.

| Падение Tray                       | Сервис продолжает работать                                  |
| Падение Service                    | WFP-блокировка сохраняется                                  |
| Перезагрузка Windows               | Блокировка восстанавливается до разрешения обычного трафика |
| Потеря VPN                         | Немедленный переход к блокировке                            |
| Сбой Process Monitor               | Разблокировка запрещена                                     |
| Повреждение config                 | Безопасные настройки по умолчанию                           |
| Отключение Ethernet                | Сохранение текущей политики                                 |
| Переключение Wi-Fi                 | Повторная проверка маршрутов и VPN                          |
| Подключение второго VPN            | Повторная идентификация защищённого маршрута                |

| Завершение запрещённого приложения | Возможность повторной разблокировки после проверки          |

Особое внимание — перезагрузке. Необходимо проверить, что до старта обычных приложений и сетевых служб не возникает промежутка с разрешённым трафиком.

## 12. Два важных решения, которые нужно зафиксировать

Первое — ручная разблокировка без VPN.

В соответствии с выбранными параметрами я закладываю следующее поведение:

- автоматическая разблокировка: только VPN работает и запрещённых процессов нет;
- ручная разблокировка: достаточно отсутствия запрещённых процессов, даже если VPN отключён;
- появление запрещённого процесса: повторная блокировка.

Таким образом, ручная разблокировка является осознанным исключением из автоматического Kill Switch.

Второе — универсальность VPN.

Поддержка любых VPN-интерфейсов должна быть целью, но гарантировать отсутствие утечек для любого стороннего VPN-клиента без дополнительной интеграции невозможно. Для production-версии нужно предусмотреть механизм обнаружения endpoint туннеля и тестовую матрицу совместимости.

## 13. Моя рекомендация по первой версии

Я бы не начинал с разработки красивого интерфейса. Самая сложная и ответственная часть — WFP и корректное определение VPN.

Приоритеты:

1. Надёжная блокировка сети.
2. Отсутствие утечек при отключении VPN.
3. Корректный контроль процессов.
4. Восстановление после перезагрузки.
5. Tray-интерфейс.

Иначе получится красивый индикатор, который показывает зелёный цвет, но не гарантирует реальную защиту.

Предлагаемый результат первой поставки: устанавливаемый MSI-пакет, Windows Service, Tray-приложение, редактируемый список запрещённых процессов и полноценная системная блокировка.

Могу следующим шагом подготовить структуру репозитория, интерфейсы C#-модулей и подробный план реализации MVP с конкретными классами, методами и последовательностью разработки.
